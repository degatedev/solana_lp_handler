#### LPH-001: Unvalidated fee_owner Address ✅

**Severity**: CRITICAL (BVSS 10.0)
**Status**: ✅ Fixed

**Original Issue**:
- The `fee_owner` parameter was not validated on-chain against the whitelist
- An attacker could set `fee_owner` to any arbitrary address and steal all protocol fees

**Fix**:
Added mandatory `fee_owner` whitelist enforcement in the security layer entry check.

**Code Change**:

```rust
// Fix location: programs/lp_handler/src/security/mod.rs:333-339
// LPH-001: Enforce on-chain that the fee_owner parameter must be present in
// the fee_owners whitelist. Otherwise an attacker can point fee_owner at any
// address and redirect all protocol fees.
require!(
    fee_owners_n != 0
        && security_config_fee_owner_contains(&data, pools_n, fee_owners_n, &fee_owner),
    LpDepositError::InvalidFeeOwner
);
```

**Effect**:
- ✅ Completely prevents attackers from supplying an unauthorized fee_owner address
- ✅ All protocol fees can only flow to whitelisted addresses
- ✅ Consistent with the existing pool whitelist mechanism

**Recommended Tests**:
1. Call the instruction with a non-whitelisted fee_owner — verify rejection
2. Call with a whitelisted fee_owner — verify normal operation
3. Attempt bypass (e.g., recipient == fee_owner) — verify it is caught

### HIGH Severity

#### LPH-003: Pre-existing Token Delegate Not Rejected at Entry ✅

**Severity**: HIGH (BVSS 7.8)
**Status**: ✅ Fixed

**Original Issue**:
- The entry phase only snapshotted the delegate without rejecting pre-existing delegates
- The default policy `forbid_delegate=true` was only checked at exit
- If the policy were changed to `false`, pre-existing delegates would be retained

**Fix**:
Reject pre-existing delegates and close authorities on signer token accounts at the entry phase.

**Code Change**:

```rust
// Fix location: programs/lp_handler/src/security/mod.rs:371-386
// LPH-003: Reject signer token accounts that already have a delegate /
// close_authority at the entry phase.
if policy.forbid_delegate {
    require_log!(
        ta.delegate.is_none(),
        LpDepositError::SecurityTokenDelegateNotAllowed,
        "entry: signer token account has existing delegate, ai.key={}",
        ai.key(),
    );
}
if policy.forbid_close_authority {
    require_log!(
        ta.close_authority.is_none(),
        LpDepositError::SecurityTokenCloseAuthorityNotAllowed,
        "entry: signer token account has existing close_authority, ai.key={}",
        ai.key(),
    );
}
```

**Effect**:
- ✅ Fails at entry rather than after business logic has already executed
- ✅ Prevents stale delegates from persisting if the policy changes in the future
- ✅ Covers both `ctx.accounts` and `remaining_accounts`

**Recommended Tests**:
1. Set a delegate before calling the instruction — verify rejection at entry
2. Set a close_authority before calling — verify rejection
3. Pass an account with a delegate via `remaining_accounts` — verify it is caught

#### LPH-004: saturating_sub Masks Arithmetic Anomalies ✅

**Severity**: HIGH (BVSS 7.2)
**Status**: ✅ Fixed

**Original Issue**:
- `saturating_sub` was used to calculate reward; when `actual < principal` it silently returned 0
- Masked abnormal situations caused by price movement
- Could be exploited to avoid fees

**Fix**:
Replace with explicit `if-else` branching and log a WARN message.

**Code Change**:

```rust
// Fix location: programs/lp_handler/src/instructions/decrease_liquidity.rs:297-320
let reward_gross_0 = if signer_token0_amount >= principal_expected_0 {
    signer_token0_amount
        .checked_sub(principal_expected_0)
        .ok_or(LpDepositError::MathOverflow)?
} else {
    msg!(
        "WARN: token0 actual_delta < principal_expected (actual={}, principal={})",
        signer_token0_amount,
        principal_expected_0
    );
    0
};
let reward_gross_1 = if signer_token1_amount >= principal_expected_1 {
    signer_token1_amount
        .checked_sub(principal_expected_1)
        .ok_or(LpDepositError::MathOverflow)?
} else {
    msg!(
        "WARN: token1 actual_delta < principal_expected (actual={}, principal={})",
        signer_token1_amount,
        principal_expected_1
    );
    0
};
```

**Effect**:
- ✅ Semantics preserved (reward only accounts for positive delta)
- ✅ Anomalous cases are explicitly logged for monitoring
- ✅ Prevents silent failures from being abused

**Recommended Tests**:
1. Simulate a price-drop scenario (actual < principal) — verify reward=0 and log is emitted
2. Normal scenario (actual > principal) — verify reward is computed correctly
3. Boundary case (actual == principal) — verify reward=0

#### LPH-005: Exit Check Does Not Re-verify Account Identity ✅

**Severity**: HIGH (BVSS 7.0)
**Status**: ✅ Fixed

**Original Issue**:
- The exit check only validated account indices, not pubkeys
- While Solana's runtime guarantees stable account references within a single instruction, defense-in-depth was lacking

**Fix**:
Changed `uninitialized_indices` to `Vec<(usize, Pubkey)>`; the exit check now verifies that the key is unchanged.

**Code Change**:

```rust
// Fix location 1: programs/lp_handler/src/security/mod.rs:80
pub uninitialized_indices: Vec<(usize, Pubkey)>,

// Fix location 2: programs/lp_handler/src/security/mod.rs:568-577
for (idx, original_key) in before.uninitialized_indices.iter().copied() {
    let ai = accounts
        .get(idx)
        .ok_or(LpDepositError::SecurityAccountSetChanged)?;

        ai.key(),
        original_key,
```

**Effect**:
- ✅ Adds a defense-in-depth layer
- ✅ Guards against potential future runtime vulnerabilities
- ✅ Improves auditability

### MEDIUM Severity

#### LPH-008: Integer Division Truncation in Reward Split ✅

**Severity**: MEDIUM (BVSS 5.5)
**Status**: ✅ Fixed

**Original Issue**:
- In `convert_to_usdc` mode, the reward split used integer division with floor truncation
- Systematic bias causing users to receive slightly more and the protocol to collect slightly less

**Fix**:
Implement round-to-nearest logic to eliminate systematic bias.

**Code Change**:

```rust
// Fix location: programs/lp_handler/src/instructions/decrease_liquidity.rs:465-483
// LPH-008: Avoid systematic bias from floor division; use round-half-up.
let quotient = num.checked_div(den).ok_or(LpDepositError::MathOverflow)?;
let remainder = num.checked_rem(den).ok_or(LpDepositError::MathOverflow)?;
let rounded = if remainder
    .checked_mul(2)
    .ok_or(LpDepositError::MathOverflow)?
    >= den
{
    quotient
        .checked_add(1)
        .ok_or(LpDepositError::MathOverflow)?
} else {
    quotient
};
rounded
    .try_into()
    .map_err(|_| error!(LpDepositError::MathOverflow))?
```

**Effect**:
- ✅ Eliminates systematic bias
- ✅ Uses `try_into` to prevent silent u128→u64 truncation
- ✅ Maintains mathematical fairness

**Recommended Tests**:
1. Quantification test: compare cumulative precision loss across many operations
2. Boundary test: remainder close to den/2
3. Overflow test: large value scenarios

## 🤔 Design Choice Explanations

### LPH-002: Unvalidated recipient Address

**Severity**: CRITICAL (BVSS 8.5)
**Decision**: Rely on frontend validation + contract verifies recipient is in the account list

**Rationale**:
1. **Trust model**: The frontend/SDK is responsible for validating the legitimacy of the recipient address
2. **Contract protection**: LPH-007 verifies that `recipient` is present in the account list for this instruction
3. **Account constraints**: Token account authority constraints provide protection at the account definition level (not runtime validation)
4. **Flexibility**: Supports legitimate scenarios where `recipient != signer`

**Risk Assessment**:
- If the frontend is compromised: funds may flow to the wrong address
- If the RPC is hijacked: the transaction may be tampered with

**Mitigations**:
- Frontend confirms the recipient address multiple times
- Use hardware wallet signing
- Display full transaction details for user confirmation before submission

---

### LPH-011: init Has No Admin Gate

**Severity**: MEDIUM (BVSS 5.0)
**Decision**: Mitigated by deployment procedure (init immediately after deploy; immutable contract)

**Rationale**:
The program is deployed as an immutable contract. The `init_security_config` call is made atomically in the same transaction as deployment, making front-running impossible. The immutable model naturally eliminates the re-initialization risk after a `close`.

---

### LPH-012: authority Is Not Rotatable

**Severity**: MEDIUM (BVSS 4.5)
**Decision**: Immutable deployment model — new version deployed periodically

**Rationale**:
The program is designed to be immutable. Key rotation is achieved by deploying a new contract version with a new authority. This provides a clear upgrade path with predictable lifecycle management, and a multi-sig wallet (e.g., Squads) is recommended as the authority to provide key recovery through member rotation.

---

### LPH-013: Token-2022 Extension Checks Not Implemented

**Severity**: MEDIUM (BVSS 4.0)
**Decision**: Relies on the pool whitelist operational review mechanism

**Rationale**:
1. **Whitelist control**: Only admin-approved pools can be used
2. **Review process**: Token properties are checked when a pool is added
3. **Implementation complexity**: Checking all extension types is costly
4. **Operational advantage**: Centralized management is more flexible

**Risk Assessment**:
- Dangerous extensions (PermanentDelegate, TransferHook) could bypass exit checks
- Requires operational team vigilance

**Mitigations**:
- Establish a pool review checklist
- Periodically audit tokens in the whitelist
- Document Token-2022 risks

---

### LPH-014: close Blocks All Operations

**Severity**: MEDIUM (BVSS 5.0)
**Decision**: Operational procedure — closing an old contract is a normal migration flow

**Rationale**:
Closing the `security_config` PDA is an intentional part of the contract migration lifecycle. When a new version is deployed, the old contract is closed as part of the transition. Users are notified in advance with clear migration guidance, and they retain the ability to interact directly with Raydium CLMM to withdraw positions if needed.

---

### LPH-019: Caller-Controlled fee_percent Allows Zero Fee

**Severity**: HIGH (BVSS 7.5)
**Decision**: Allowed by business design (flexible fee mechanism)

**Rationale**:
1. **Business flexibility**: Supports different fee strategies for different scenarios
   - Promotional events: 0% fee to attract users
   - Large transactions: negotiated fee rate
   - Special partnerships: custom fee rate
2. **Trust model**: The frontend/SDK controls the fee rate parameter
3. **Competitive advantage**: Fee strategy can be adjusted to market conditions

**Risk Assessment**:

### LPH-020: Fee Rounding Exploitable via Micro-Transactions

**Severity**: LOW (BVSS 2.0)
**Decision**: Not fixed (economically infeasible)

**Rationale**:
1. **Economically infeasible**: Solana transaction fees are approximately 5,000 lamports
2. **Negligible precision impact**: For tokens with 6+ decimals, 100 units is nearly negligible
3. **Code complexity**: Adding a minimum fee would increase edge-case handling

**Risk Assessment**:
- At `fee_percent=1` (0.01%), fee becomes 0 only when reward < 10,000 units
- For USDC (6 decimals), this corresponds to $0.01

**Mitigations**:
- Monitor for abnormal micro-transaction patterns
- Set a reasonable minimum fee rate (e.g., 0.1%)
